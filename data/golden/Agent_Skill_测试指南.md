# Agent Skill 测试数据模拟指南

## 概述

生成的 Agent Skill (SKILL.md) 加载到 Hermes / OpenClaw 后，需要一批**测试案例**来验证它的判断质量。
本指南教你如何设计测试案例、构造测试数据、并利用 `verification_runs` 表做量化评估。

---

## 一、测试案例设计原则

每条测试案例 = 一个"案件"，Agent 读后输出评估，与 golden 知识做对比。

### 案例四要素

```
CASE-001 | 场景描述 (含关键数据点) | golden 专家结论 | 预期匹配的知识条目
```

**示例**：

```
CASE-001 | 芯片设计企业成立4年，营收年增35%，申报高新技术企业，
           申请500万纯信用贷款。最近12个月流水显示每季度末最后一周
           有一笔大额转入、短期后又转出。 | 降额至200万 + 追加个保 | KN-008, KN-023

CASE-002 | 传统制造企业成立8年，营收稳定年增5%，有厂房可抵押，
           申请续贷300万。征信良好，流水与纳税一致。 | 正常审批通过 | KN-002
```

### 测试数据覆盖矩阵

| 意图 | 案例特征 | 验证什么 |
|------|---------|---------|
| **常规判断** | 完全符合准入条件 | Skill 是否误报风险 |
| **边界模糊** | 刚好踩在准入线上 (成立刚满1年) | Skill 是否识别灰色地带 |
| **隐性信号** | 表面漂亮但有异常模式 | Skill 能否抓到反模式 |
| **破例判断** | 按规则该拒但有特殊价值 | Skill 能否给出破例建议 |
| **空数据** | 关键数据缺失 (无纳税记录) | Skill 能否提示缺失字段 |

每种意图至少 2 条案例，共 10 条以上最小测试集。

## 二、用 golden 知识库反推测试案例

已有的 29 条 golden_items 天然定义了测试范围——**每条知识应该有一条案例验证它能被正确触发。**

### 示例：从 golden 知识反推案例

**golden 知识** (KN-025): 评估科技初创企业时重点测算现金安全垫——账上可用现金除以月均消耗。

**反推测试案例**：
```
CASE-025-OK | 生物医药企业，成立2年，账面现金6000万，月均消耗400万，
              已获VC融资1.2亿，CEO为清华博士。申请信用贷款300万。 | 通过 | KN-025, KN-026

CASE-025-NG | 生物医药企业，成立1年，账面现金800万，月均消耗250万，
              无VC背书，核心技术未获临床批件。申请信用贷款500万。 | 拒绝 | KN-025, KN-027
```

一条 golden 知识 → 一正一反两个测试案例。29 条 golden_items → 58 条测试案例。

## 三、测试数据文件格式

### 格式 A: 简易文本 (用于页面「显性化校验」功能)

```
案例ID,场景描述,专家结论
CASE-001,芯片设计企业成立4年流水异常申请授信500万,降额+个保
CASE-002,传统制造企业成立8年流水稳定申请续贷,通过
CASE-003,生物医药成立2年账面现金充足有VC背书申请300万,通过
```

直接粘贴到 Step4 的「显性化校验回放」文本框。

### 格式 B: JSON (用于脚本自动化测试)

```json
{
  "scenario_id": 1,
  "test_name": "Skill 基础判断测试集 v1",
  "cases": [
    {
      "case_id": "CASE-001",
      "scenario_text": "芯片设计企业成立4年，营收年增35%，申报高新技术企业，申请500万纯信用贷款。最近12个月流水显示每季度末最后一周有一笔大额转入、短期后又转出。",
      "expert_conclusion": "降额至200万+追加个保",
      "expected_category": "降额",
      "expected_golden_items": ["KN-008", "KN-023"],
      "notes": "反模式案例 —— 流水异常信号"
    }
  ]
}
```

## 四、使用 `verification_runs` 量化评估

### 评估流程

```
生成 Agent Skill → 部署到 Agent 平台
                      ↓
              提交测试案例集 (JSON 格式)
                      ↓
        Agent 逐案输出: { 匹配知识ID, 置信度, 建议动作, 缺失字段 }
                      ↓
        与 golden 结论对比 → 填入 verification_runs
                      ↓
        产出: precision / recall / F1 / 字段匹配率
```

### 手动对照表 (脚本化前的过渡方案)

| 字段 | 含义 | 来源 |
|------|------|------|
| total_golden_items | 此场景 golden 知识总数 | golden_items COUNT |
| matched_items | Agent 命中的 golden 条目 | 人工对比 |
| pipeline_total | Agent 总共输出的条目数 | Agent 输出 |
| precision | matched / pipeline_total | 是否有假阳性 |
| recall | matched / total_golden | 是否漏报 |
| f1_score | 2×P×R/(P+R) | 综合评分 |

### 插入记录示例

```sql
INSERT INTO verification_runs
(scenario_id, pipeline_id, step, total_golden_items, matched_items, pipeline_total, precision, recall, f1_score)
VALUES
(1, 'sk_test_001', 4, 29, 22, 25, 88.0, 75.9, 81.5);
```

## 五、测试集维护策略

| 维护操作 | 触发条件 | 动作 |
|---------|---------|------|
| 添加案例 | 新 golden 知识入库 | 为每条新知识添加 1-2 条测试案例 |
| 淘汰案例 | golden 知识被标记为过时 (突破数≥3) | 标记案例为 archived |
| 难度升级 | F1 稳定 > 90% | 增加「多信号叠加」「故意缺失关键数据」等刁钻案例 |
| 版本对比 | Skill 重新生成 | 同一份测试集对两个版本的 Skill 各跑一次，对比 F1 变化 |

## 六、生产就绪 Checklist

- [ ] 测试案例 ≥ 50 条 (覆盖所有环节)
- [ ] 正面案例与反面案例 ≥ 1:1
- [ ] 至少 5 条"故意缺失关键数据"的案例
- [ ] 至少 3 条"多信号叠加"的复杂案例
- [ ] verification_runs 有 ≥ 2 次不同版本的运行记录
- [ ] F1 ≥ 80%
- [ ] recall ≥ 75% (Agent 不能大量漏报)
- [ ] 保鲜度审计未标出 critical 缺口
