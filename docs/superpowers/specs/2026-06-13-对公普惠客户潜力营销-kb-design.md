## 1. 背景与目标

用户希望基于一份面向“普惠客户潜力营销”的访谈提纲模板，构建一个**对公普惠客户潜力营销**场景的知识库，并生成验证流水线所需的输入数据。

该提纲的核心圈客逻辑是**逐层推进**的：

1. **客户筛选**：从网点存量客户中圈出科技型、未办理普惠信用快贷的客户。
2. **客户数据匹配**：叠加成立年限、实控人年龄、征信、他行信贷等准入/风险数据字段。
3. **原因归因**：对未办理原因进行分类（无融资需求、不满足准入条件、产品匹配度不足/未深度触达）。
4. **决策建议**：根据归因结果输出差异化营销策略与产品推荐。

最终生成的 Skill 执行逻辑也应严格遵循这 4 层结构。

---

## 2. 设计决策

### 2.1 选型：Layered IR entries（分层 IR 条目）

我们选择把 4 层圈客逻辑直接映射为 4 组 `KN-xxx` 条目，每层再按具体规则/原因/动作拆细。

**原因**：

- 与访谈提纲的“逐层”结构一致，Skill 可逐层检索、逐层判断。
- 验证流水线能精准定位失败层，并生成针对性的 revision suggestions。
- 便于后续专家在 Step3 知识对齐时逐条确认、修订或合并。

**未选方案**：

- **子场景大条目**：颗粒度太粗，验证命中后无法精确修订。
- **混合方案**：虽有灵活性，但会带来信息冗余；本场景 4 层结构清晰，无需额外复合条目。

### 2.2 场景边界

- **场景名称**：对公普惠客户潜力营销
- **场景说明**：基于网点存量对公客户，识别具备科技资质但未办理普惠信用快贷的潜在客户，通过数据匹配与原因归因，输出分层营销建议。
- **子场景**：科技型企业普惠贷款营销（示例：网点现有对公客户中，具有科技资质且未申请普惠信用快贷的客户名单及原因，给出营销建议）
- **不纳入范围**：
  - “风险”sheet 的贷后/预警内容（本次仅使用“营销”sheet）。
  - 其他银行/非建设银行的规章制度细节（保留可替换占位符，如 `X 年`、`X 万`）。

## 4. 知识库条目结构

沿用项目现有 `scenario-schema.yaml` 字段，每个条目至少包含以下字段：

| 字段 | 说明 | 示例 |
|---|---|---|
| `环节` | 所属圈层 | 客户筛选 |
| `具体方法` | 操作方法/数据源 | 筛选网点归属、账户状态、科技资质标签、未办贷标志 |
| `判断逻辑` | 可执行规则 | 同时满足：机构=当前网点、状态=正常、科技标签任一=1、授信客户标志≠1 |
| `知识类型` | 判断规则 / 操作流程 / 反模式 | 判断规则 |
| `适用条件` | 何时适用 | 网点存量对公客户 |
| `反模式/踩坑提示` | 常见错误 | 不要只看科技标签，需确认账户状态；避免把已授信客户重复圈入 |
| `经验判断` | 专家经验 | 优先联系成立年限>2 年且结算活跃的科技型企业 |
| `适用边界` | 边界 | 仅适用于未办理普惠信用快贷的客户 |
| `例外情形` | 例外 | 集团客户已在他行办理类似产品、客户近期有销户计划 |
| `来源文档` | 来源文件名 | 科技型企业普惠贷款营销访谈提纲模板.xlsx |
| `来源位置` | 来源位置 | 营销 sheet / 步骤 1 客户筛选 |
| `置信度` | 高/中/低 | 高 |
| `证据数 / 突破数` | 证据/反例数量 | 1 / 0 |

### 4.1 条目分层规划（约 15 条）

| 层级 | 条目数 | 关键条目 |
|---|---|---|
| 客户筛选 | 3 | 网点+状态筛选、科技资质标签判定、未办理普惠信用快贷判定 |
| 客户数据匹配 | 4 | 成立年限、实控人年龄、征信记录、他行信贷合作 |
| 原因归因 | 4 | 无融资需求判定、不满足准入条件、产品额度/利率不匹配、未深度触达/资金缺口 |
| 决策建议 | 4 | 无需求→结算/投资产品、不满足准入→材料补充、不满足准入→持续跟踪、产品不匹配→替代产品 |

## 5. 验证流水线输入

### 5.1 测试用例格式

每个 test case 是一个 JSON 文件，包含：

```json
{
  "case_id": "case-phmarketing-01",
  "scenario": "对公普惠客户潜力营销",
  "description": "某科技型企业，成立 3 年，账户状态正常，金融总量 800 万，活期+定期日均 120 万，无申贷记录，未办理信用快贷",
  "expert_conclusion": "通过-客户无融资需求；建议推荐现金池、大额存单等结算/投资产品",
  "expected_rules": ["KN-005", "KN-009", "KN-013"]
}
```

### 5.2 测试用例规划

| 用例 ID | 覆盖归因 | 关键字段 |
|---|---|---|
| `case-phmarketing-01` | 无融资需求 | 金融总量高、无申贷记录 |
| `case-phmarketing-02` | 不满足准入条件 | 成立年限不足 / 征信瑕疵 |
| `case-phmarketing-03` | 产品匹配度不足 | 申贷次数>0、预测算额度低、净流出大 |

### 5.3 验证目标

验证目标优先级：

1. 对齐后的 Skill IR JSON（`step4_skill_ir_file`）。
2. 渲染后的 `SKILL.md` / `COT.md`。
3. 备用：本知识库的 golden 条目。

验证指标沿用项目默认：命中率、字段匹配率、置信度分布。

---

## 6. 使用方式

1. **导入样本**：把 `data/samples/` 下的新场景文件放入项目对应目录。
2. **导入 golden**：使用 `backend/tools/` 下的导入脚本（或 SQLite 直接写入）把 `data/golden/对公普惠客户潜力营销_golden_items.json` 写入 `data/golden/golden_test.db`。
3. **创建流水线**：在 UI 或 API 新建 pipeline，选择场景“对公普惠客户潜力营销”。
4. **运行验证**：在 Step5 验证页面加载 `data/test-cases/case-phmarketing-*.json`，运行 replay。
5. **迭代修订**：若命中率低于 `config/scenario-schema.yaml` 中的阈值，根据 `revision_suggestions_*.json` 回灌 Step3 进行知识对齐。

## 7. 验收标准

- [ ] 新建场景目录与源文档已创建并符合项目 sample 规范。
- [ ] golden 条目 JSON 包含 12–16 条 `KN-xxx`，字段完整、层级清晰。
- [ ] 3 个 test cases 覆盖三种主要归因结论。

- [ ] 命中率达到或超过 `config/scenario-schema.yaml` 中配置的 `quality.replay_hit_threshold`（默认 0.8）。

---

## 8. 风险与假设

- 规章中的具体阈值（如成立年限 X 年、X 周岁、X 万）在提纲中未给出具体数值，知识库中将保留占位符，并在 IR 条目中标注“需本地配置”。
- 如果后续把“风险”sheet 也纳入，需要新增贷后预警子场景，届时可扩展本设计。
